### 14:59 @unknown

Day 60 — Becoming AI Engineer  Today I added a Swarm Manager to my multi-agent AI engineering project and learned that building intelligent systems is not only about creating powerful agents—it is also about designing how they collaborate.  Before today, I viewed multi-agent systems mostly as a collection of specialized agents working together through predefined workflows.  After studying swarm intelligence and hierarchical architectures, I realized that the hardest problem is not building the agents themselves. It is designing the coordination layer between them.  The biggest lesson:  AI engineering is as much about orchestration as it is about intelligence.  I learned that there are multiple coordination patterns in multi-agent systems, and each solves a different problem.  The first pattern is Swarm Architecture.  A swarm is a collection of agents that collaborate without a permanent central controller. Instead of following a fixed workflow, agents make local decisions and dynamically decide how work should be completed.  The four characteristics that define a swarm are:  • Peer-to-peer communication between agents.  • No permanent central controller managing every decision.  • Dynamic task assignment based on the current problem.  • Emergent collaboration where workflows are created through local agent decisions rather than predefined pipelines.  One realization completely changed my understanding of distributed decision-making.  It does not mean every agent participates in every decision.  Instead, every agent continuously asks simple questions:  • Can I solve this task myself?  • Do I need another specialist agent?  • Which agent should I delegate to?  • Am I finished or should I continue reasoning?  Complex workflows emerge from many small local decisions made independently by multiple agents.  I also learned that swarms are dynamic by design.  Today's task may be solved through:  Agent A → Agent C → Agent D  while tomorrow's task may become:  Agent B → Agent A → Agent E  There is no hardcoded execution path. Agents self-organize based on the requirements of the problem.  The second coordination pattern I studied was Hierarchical Architecture.  Unlike swarms, hierarchical systems provide clear organizational structures.  A top-level agent delegates work to supervisor agents, and those supervisors manage their own specialized teams.  Control flows from the top down:  CEO Agent → Department Head → Specialized Team → Worker Agents  Hierarchies provide predictability, accountability, and structured goal decomposition.  Another important concept I learned was A2A (Agent-to-Agent Protocol).  A2A is not a coordination pattern.  It is the communication layer that allows independent agents and teams to communicate across different processes, machines, and organizations.  Whether we build swarms or hierarchies, A2A becomes the transport layer that connects everything together.  I also studied the runtime orchestration components responsible for executing multi-agent systems:  • Router → decides where requests should be sent.  • Scheduler → decides when and in what order tasks should execute.  • Executor → performs the actual work.  These components form the operational backbone of production multi-agent architectures.  The most interesting realization came when combining all of these concepts into a single architecture.  My current design looks like this:  CEO Agent (Hierarchy) → Engineering Head → Marketing Head → Sales Head Each department contains: Supervisor Agent → Swarm Manager → Specialized ReAct Agents Each individual agent contains its own reasoning loop:  Reason → Act → Observe → Repeat  And A2A provides communication between independent services and teams. This hybrid architecture combines the strengths of multiple design patterns: • Hierarchy provides organizational control and goal decomposition.  • Swarms provide flexibility and dynamic problem solving.  • ReAct provides reasoning capabilities for individual agents.  • A2A enables communication between distributed systems.  The biggest takeaway from today:  Building AI agents is only one layer of AI engineering.  Production systems require designing how intelligence is organized, coordinated, communicated, and executed across multiple layers of abstraction.  AI engineering is slowly becoming less about building individual models and more about building intelligent systems.  Today was another step toward understanding how production-grade multi-agent architectures are designed.  Next: Completing the hybrid Swarm + Hierarchical + A2A multi-agent architecture and exploring observability, scheduling, and production orchestration patterns for scalable AI systems.  #AIEngineering #ArtificialIntelligence #AgenticAI #MultiAgentSystems #SwarmIntelligence #A2A #ReAct #LLM #GenerativeAI #SoftwareEngineering #AIInfrastructure #BuildingInPublic

Transformers struggle to generalize to tasks they were not explicitly trained on. Instead, we propose in 2026 that it is the job of the harness to generalize through composition.  We observe a powerful property when training RLMs: for tasks with shared structure that look different, the root model naturally learns the same trajectory, meaning it views the two task trajectories as the same! In other words, the Transformer does not need additional generalization capabilities to transfer capabilities from one task to the other, the harness induces it.  We find that well-designed harnesses form a quotient set over task trajectories, meaning their individual LLM calls can see structurally “similar” tasks as near-identical, token-for-token! Harnesses can effectively generalize for the Transformer during training, without relying on any intrinsic generalization capability from the model.  For example, RLMs can see problems of different lengths as the same: we show that RLMs can train exclusively on short tasks, and fully generalize to similar but unseen tasks 8-32x longer because it produces near identical trajectories for both.  Taking this further, we show that tasks across different domains (e.g. math solutions vs. essay writing) that share a decomposition strategy exhibit the same generalization effect. RLMs can train on the problem of finding which essays belong to the same author and improve performance on finding math problems that share similar solutions. One pattern I find useful for working with LLMs is a nice long ramble session. Sometimes the LLM needs more bits to understand what you're trying to achieve, but you're too lazy to type them. In these cases I like to lean back, switch to /voice and just ramble for like 10 minutes, total mess, anything goes, full stream of consciousness. Sometimes I declare it up top, something like "switching to speech recognition sorry for any typos...". Sometimes I turn it into a small interview of a few turns. But I find that the LLMs are somehow very good at reconstructing long incoherent rambles and often their echo of your own tangle of thoughts comes out quite a bit cleaner than what you started with. The result is that you improve the mind meld and have to correct things less from that point on.
