LLM Knowledge Bases  Something I'm finding very useful recently: using LLMs to build personal knowledge bases for various topics of research interest. In this way, a large fraction of my recent token throughput is going less into manipulating code, and more into manipulating knowledge (stored as markdown and images). The latest LLMs are quite good at it. So:  Data ingest: I index source documents (articles, papers, repos, datasets, images, etc.) into a raw/ directory, then I use an LLM to incrementally "compile" a wiki, which is just a collection of .md files in a directory structure. The wiki includes summaries of all the data in raw/, backlinks, and then it categorizes data into concepts, writes articles for them, and links them all. To convert web articles into .md files I like to use the Obsidian Web Clipper extension, and then I also use a hotkey to download all the related images to local so that my LLM can easily reference them.  IDE: I use Obsidian as the IDE "frontend" where I can view the raw data, the the compiled wiki, and the derived visualizations. Important to note that the LLM writes and maintains all of the data of the wiki, I rarely touch it directly. I've played with a few Obsidian plugins to render and view data in other ways (e.g. Marp for slides).  Q&A: Where things get interesting is that once your wiki is big enough (e.g. mine on some recent research is ~100 articles and ~400K words), you can ask your LLM agent all kinds of complex questions against the wiki, and it will go off, research the answers, etc. I thought I had to reach for fancy RAG, but the LLM has been pretty good about auto-maintaining index files and brief summaries of all the documents and it reads all the important related data fairly easily at this ~small scale.  Output: Instead of getting answers in text/terminal, I like to have it render markdown files for me, or slide shows (Marp format), or matplotlib images, all of which I then view again in Obsidian. You can imagine many other visual output formats depending on the query. Often, I end up "filing" the outputs back into the wiki to enhance it for further queries. So my own explorations and queries always "add up" in the knowledge base.  Linting: I've run some LLM "health checks" over the wiki to e.g. find inconsistent data, impute missing data (with web searchers), find interesting connections for new article candidates, etc., to incrementally clean up the wiki and enhance its overall data integrity. The LLMs are quite good at suggesting further questions to ask and look into.  Extra tools: I find myself developing additional tools to process the data, e.g. I vibe coded a small and naive search engine over the wiki, which I both use directly (in a web ui), but more often I want to hand it off to an LLM via CLI as a tool for larger queries.   Further explorations: As the repo grows, the natural desire is to also think about synthetic data generation + finetuning to have your LLM "know" the data in its weights instead of just context windows.  TLDR: raw data from a given number of sources is collected, then compiled by an LLM into a .md wiki, then operated on by various CLIs by the LLM to do Q&A and to incrementally enhance the wiki, and all of it viewable in Obsidian. You rarely ever write or edit the wiki manually, it's the domain of the LLM. I think there is room here for an incredible new product instead of a hacky collection of scripts.

### 14:12 @unknown

Why do LLMs use Softmax at the output? Let's understand.  An LLM has a huge vocabulary (let's say 50,000 tokens). At each step, it must pick the next token from this list.  But the model does not directly output probabilities. It outputs a raw score for each token, called a logit.  A logit can be any number - positive, negative, very large, or very small.  So, how do we pick the next token from raw numbers? The answer is Softmax.  Softmax converts these raw logits into a clean probability distribution.  It does two important things: - Makes every value lie between 0 and 1 - Makes all values sum to exactly 1  Let's say we have three tokens with logits [2.0, 1.0, 0.1].  After applying Softmax, we get something like [0.66, 0.24, 0.10]. These are valid probabilities. They sum to 1.  Now we can directly say: this token has a 66% chance, that one has a 24% chance, and so on.  Now, the question is, why is this useful?  - We can sample the next token based on these probabilities. - We can apply temperature, top-k, or top-p to control creativity. - During training, we can compare these probabilities with the correct answer using cross-entropy loss.  Softmax also amplifies differences. A slightly bigger logit gets a much bigger probability, and smaller logits get pushed close to zero. So, the model strongly prefers the top-scoring tokens, but still gives a small chance to others.  So, Softmax turns raw numbers into a clean probability distribution that the model can sample from.  That is why every LLM uses Softmax at the output layer.

Why do LLMs have so many parameters? Let's understand.  A modern LLM has billions, even trillions, of parameters.   But what is a parameter, and why do we need so many?  A parameter is a single learnable number inside the model. Think of it as a tiny knob the model can adjust.  These knobs are spread across every layer of the Transformer - inside attention, feed-forward blocks, and embeddings.  During training, we slowly turn each knob to reduce the prediction error.  Now, the question is, why do we need billions of them?  The job of an LLM is huge. It must capture: - Grammar of every language - Facts about the world - Reasoning patterns - Code, math, and logic - Style, tone, and intent  Each parameter stores a tiny piece of this knowledge. More parameters give the model more room to store patterns.  A model with a few million parameters can learn a small task. But it cannot hold the patterns of the entire internet.  So, here comes the scaling law into the picture. As we increase parameters, data, and compute together, the model gets significantly better.  Bigger models capture deeper relationships between words, longer dependencies, and more nuanced reasoning. They learn what small models cannot.  But, here is the catch. More parameters means more memory, more training cost, and more inference cost. We cannot just keep adding parameters - we must scale data and compute alongside.  This is why modern LLMs are built with billions of parameters. They need that much room to store the patterns of the world.  More parameters, more knowledge, more capability.

Most people think ChatGPT “just generates text.”  It doesn’t.  What actually happens after you press Enter is one of the most insane distributed systems ever built.  A modern LLM pipeline is basically:  mathematics  * GPU architecture * memory engineering * probability theory * systems design * compression * parallel computing  …all happening in milliseconds.  Here’s the full mental model 👇  ━━━━━━━━━━━━━━━━━━━  1. TOKENIZATION  Your prompt is broken into tokens.  Not words. Not characters.  Tokens.  Example:  “Transformers changed AI forever”  might become:  ["Transform", "ers", " changed", " AI", " forever"]  Then every token gets converted into an integer ID.  The model never sees language directly.  It only sees numbers.  This is also why LLMs struggle with: → counting letters → exact spelling logic → character-level reasoning  Because language is compressed before reasoning even starts.  ━━━━━━━━━━━━━━━━━━━  2. EMBEDDINGS  Now those token IDs become vectors.  Huge vectors.  Something like:  4096-dimensional floating point representations.  At this stage:  Language → Geometry  Words with similar meaning cluster together in vector space.  King and Queen end up “near” each other mathematically.  This is the moment text becomes machine-understandable.  ━━━━━━━━━━━━━━━━━━━  3. POSITIONAL ENCODING  Transformers don't naturally understand sequence.  Without positional encoding:  # “The dog bit the man”  “The man bit the dog”  Same tokens. Different meaning.  So the model injects positional information into embeddings.  Now the model understands order, structure, and flow.  ━━━━━━━━━━━━━━━━━━━  4. TRANSFORMER BLOCKS  This is where the real computation happens.  Repeated 96+ times in large models.  Each block contains:  → Self-Attention → Feed-Forward Networks → Residual Connections → Layer Normalization  Over and over again.  Every layer deepens the representation.  Early layers: grammar + syntax  Middle layers: facts + relationships  Later layers: reasoning + abstraction  This is where intelligence emerges.  ━━━━━━━━━━━━━━━━━━━  5. SELF-ATTENTION  The breakthrough that changed AI.  Every token looks at every other relevant token.  The model dynamically decides:  “What matters most right now?”  Example:  “Apple released new chips and its stock jumped.”  Self-attention helps the model know: “its” = Apple  Not chips.  Attention is basically dynamic context lookup.  And it scales brutally.  Context length doubles? Attention cost explodes quadratically.  That’s why long-context inference is so expensive.  ━━━━━━━━━━━━━━━━━━━  6. KV CACHE  This is the part most people completely miss.  During generation, the model stores:  → Keys → Values  from previous tokens.  Why?  Because recomputing attention over the entire conversation every step would be impossibly slow.  So instead:  previous computations are cached.  This makes autoregressive generation feasible.  But there’s a catch:  KV Cache grows linearly with context length.  More context = more VRAM consumed = harder inference scaling.  This is one of the biggest infrastructure bottlenecks in modern AI.  ━━━━━━━━━━━━━━━━━━━  7. PREFILL vs DECODE  These are fundamentally different workloads.  Most people incorrectly treat inference as one thing.  It’s actually two separate phases:  A) PREFILL PHASE Processing the entire prompt.  This is: → massively parallel → compute-bound → GPU utilization heavy  B) DECODE PHASE Generating tokens one at a time.  This is: → sequential → memory-bandwidth bound → latency-sensitive  Optimizing one does NOT optimize the other.  This distinction explains: → why inference is expensive → why latency is hard → why serving LLMs is an infrastructure nightmare  ━━━━━━━━━━━━━━━━━━━  8. SAMPLING  The model doesn’t “choose words.”  It outputs probabilities.  For every next token:  128K+ possible candidates.  Sampling strategies decide how deterministic or creative the output becomes.  → Greedy Always pick highest probability.  → Temperature Controls randomness.  → Top-K Sample from top K candidates only.  → Top-P Sample from smallest probability mass.  Tiny parameter changes completely alter behavior.  Same model. Different personality.  ━━━━━━━━━━━━━━━━━━━  9. SPECULATIVE DECODING  One of the smartest tricks in modern inference.  A small draft model predicts multiple tokens ahead.  Then the large model verifies them in parallel.  If correct:  You generate 4-5 tokens for nearly the cost of 1.  This massively increases throughput.  Modern LLM speedups increasingly come from systems engineering — not just larger models.  ━━━━━━━━━━━━━━━━━━━  10. STREAMING  Finally:  Token IDs convert back into text.  And stream to your screen.  That “typing” effect?  Not animation.  Actual incremental decoding happening live.  One token at a time.  ━━━━━━━━━━━━━━━━━━━  What’s crazy is that ALL of this happens in milliseconds:  → tokenization → embeddings → attention → caching → sampling → decoding → streaming  across thousands of GPUs.  Every ChatGPT response is basically a real-time distributed supercomputer pipeline disguised as a chat window.  And we’re still in the early versions of this architecture.  The next decade of AI infrastructure will probably be defined by:  → better memory systems → faster inference → cheaper decoding → longer context handling → smarter routing → multimodal token pipelines  The models get the attention.  But the infrastructure is where the real war is happening.  Which part of the pipeline surprised you the most?
