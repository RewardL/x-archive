The core skills he listed were spec design, eval loops, and security oversight.  The problem is that production agents don't run on the agent code alone. They need a model provider, a retrieval layer, an eval system, a deployment target, and observability.  And normally, these are scattered across different dashboards, config files, and tools, each with its own setup and learning curve.  The solution to production-grade Agentic Engineering is now actually implemented in Google’s Agents CLI.  It covers the entire lifecycle in a single interface, covering scaffolding, evaluating, and deploying ADK agents.  The setup command injects 7 ADK-specific skills into a coding agent's context, which lets it handle scaffolding, evals, deployment, and enterprise registration through natural language.  I mapped the whole thing end-to-end in the diagram below. Here is what each layer is doing:  > Agent Orchestration defines the agent using the ADK, and the A2A protocol handles coordination when one agent needs to invoke another. ADK is model-agnostic, so the models cover Gemini, Gemma, and third-party models like Claude, via Model Garden.  > The data layer handles retrieval. Vector Store stores the embeddings for RAG, and the ingestion pipeline loads and chunks docs into it. Monitoring and storage happen alongside it.  > The evaluation layer runs the agent against test scenarios with LLM-as judge scoring. It runs before deployment.  > For deployment, you can choose between Agent Runtime, Cloud Run, etc., depending on how much control you need. Agents CLI configures across all targets.  > Finally, teams that need staging and production environments, the IaC and CI/CD layer handles infrastructure as code and deployment pipelines.  Every one of these layers is a service that a dev would otherwise configure manually.  But Google's Agents CLI ties them together to make the full agentic engineering lifecycle practical. Q❯ LLMへの入力が学習に使われる可能性があるというけれども、具体的にどのように学習に使われるのですか？ 例えば私がLLMに嘘を教えたらそれを学習してしまう可能性があるのですか？  Fable❯ いい質問です。ここは誤解が多いところなので、順を追って説明します。  まず大前提：会話中にリアルタイムで学習はしない  LLMのパラメータ（重み）は推論時には固定されています。あなたが会話の中で嘘を教えても、その場でモデルの「知識」が書き換わることはありません。同じ会話の中で嘘を前提に応答が続くのは、文脈（コンテキスト）として参照しているだけで、会話が終われば消えます。他のユーザーの会話にも影響しません。  「学習に使われる」とは具体的に何をするのか  事業者が「入力を学習に使う」と言う場合、典型的には次のような流れです。  1. 収集・保存—会話ログ（入力と応答、場合によっては評価ボタンの反応）を保存する 2. フィルタリング—個人情報の除去・マスキング、重複除去、品質や有害性による選別 3. 将来のモデルの訓練データに混ぜる—事前学習コーパスの一部にする、あるいはファインチューニング（SFT）や強化学習（RLHF）用のデータ作りの材料にする。「どんな質問にどう答えると良い評価だったか」という嗜好データとして使われることも多い  つまり反映されるのは次にリリースされるモデルであって、今使っているモデルではありません。数ヶ月〜年単位のタイムラグがあります。  嘘を教えたら学習してしまうか  理論上は可能ですが、実際には一人の入力が事実として定着する可能性は非常に低いです。理由は：  - 訓練データは数兆トークン規模で、あなたの一つの発言はその中の砂粒一つです。モデルの「知識」は大量のデータ全体の統計的な傾向として形成されるので、単発の嘘は既存の大量の正しい情報に埋もれます - 収集データはそのまま使われるのではなく、選別・加工を経ます。ユーザー入力はむしろ「どんな質問が来るか」の実例として使われることが多く、内容を事実として鵜呑みにする形で使われるとは限りません  ただし、注意すべき例外もあります：  - 他に情報源がない固有の情報（珍しい人名や独自の文字列など）は、対抗する正しいデータがないため、丸暗記（memorization）されて再現されるリスクが相対的に高い。個人情報を入力しないよう言われるのはこのためです - 組織的な大量投稿（データポイズニング）なら統計を歪められる可能性があり、実際に研究対象になっています。Web上に偽情報を大量に置いてクロールさせる攻撃も同じ構図です  実際の運用について  事業者やプランによって扱いは違います。例えばAnthropicの場合、APIや法人向けの入力はデフォルトでは訓練に使われず、個人向けClaudeでは訓練への利用可否をユーザーが設定で選べます。他社も概ね「消費者向けはオプトアウト方式、API・法人向けは不使用がデフォルト」という構図が多いですが、利用しているサービスの規約を確認するのが確実です。  要するに、「嘘を教えたらモデルが騙される」という心配より、「二度と出てほしくない固有の情報（秘密やパスワード、個人情報）を入力しない」ことのほうが実務上は重要です。
