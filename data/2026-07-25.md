ONE PROMPT TURNED A 5 MINUTE AI WORKFLOW INTO 40 PARALLEL TASKS AND FINISHED THE SAME JOB IN 14.2 SECONDS  00:01 the orchestrator splits one audit across 40 workers in 6 categories, and every independent task starts at once while only the final report waits.  the old setup forces 40 calls to run one after another. at roughly 8 seconds each, that creates more than 5 minutes of latency even though most tasks never use each other’s output.  graph engineering removes those fake dependencies. the terminal keeps only 3 real edges, runs all 40 workers concurrently and cuts 320 seconds of sequential work down to 14.2 seconds.  each node handles one job and returns structured output. once all checks finish, the graph groups them into 2 batches and merges the summaries into one severity report.  the speedup comes from making latency depend on the slowest layer instead of adding every call together. the model, prompts and underlying work stay exactly the same.  bookmark this before your next multi-agent workflow spends five minutes doing a fourteen-second job.

10 EVALS DE AGENTES PARA INGENIEROS DE IA  (evals = evaluaciones de agentes, explicadas con su caso de uso)  1. golden set → un set fijo de casos que nunca editas, lo ejecutas en cada cambio → úsalo como la línea base que te dice si algo se movió  2. llm as judge → un segundo modelo puntúa la salida contra una rúbrica escrita → úsalo cuando la respuesta es abierta y no hay string contra el que comparar  3. rubric scoring → un número por dimensión: correctitud, tono, seguridad, coste → úsalo cuando una sola nota esconde qué parte empeoró de verdad  4. trajectory eval → evalúa el camino que tomó el agente, no solo la respuesta a la que llegó → úsalo cuando acertar por el motivo equivocado te va a pasar factura después  5. tool unit tests → testea cada herramienta por separado, con fixtures, sin modelo de por medio → úsalo siempre. la mayoría de bugs de agentes son bugs de tools disfrazados  6. regression suite → replica ejecuciones pasadas contra el nuevo prompt o modelo y compara resultados → úsalo antes de cada cambio de prompt, porque los prompts no tienen sistema de tipos  7. a/b en producción → divide tráfico real entre dos versiones y compara resultados, no sensaciones → úsalo cuando las métricas offline dejaron de predecir lo que hacen los usuarios  8. human review → coge una muestra de ejecuciones y que una persona las puntúe con honestidad → úsalo para calibrar tu judge, porque un judge que nadie revisa se desvía en silencio  9. shadow run → el candidato corre sobre tráfico real en paralelo y su salida no se le enseña a nadie → úsalo antes de un despliegue arriesgado, cuando una sola respuesta mala sale cara  10. red team → atácalo a propósito: jailbreaks, injection, exfiltración, abuso de tools → úsalo antes de que alguien externo pueda llegar a él, no después  las evals offline te dicen que funciona. las online te dicen que sigue funcionando.  guárdate esto. luego lee el desglose completo en loop engineering abajo.
